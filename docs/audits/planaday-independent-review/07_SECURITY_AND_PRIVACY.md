# Security and privacy review

The review used source inspection, dependency and deployment configuration review, and normal synthetic workflows. This report describes the security boundaries that need repair and the defensive acceptance conditions. Deployed network reachability and abuse behavior were outside verification.

| Finding | Evidence | Defensive control |
|---|---|---|
| P0 · Sync and storage have no application identity or authorization | `server/index.ts:34–38, 138–219, 248–279` registers broad CORS and sensitive routes without an authentication/authorization hook. Caller device IDs identify changes. `docker-compose.yml:9–10` publishes the port. | Agree on a local single-user pairing model and authenticated shared mode. Require origin allowlists, encrypted transport appropriate to deployment, scoped authorization on records/blobs/admin actions, and restrictive bind defaults. Maintain offline operation. |
| P0 · Worker is insufficient as the sole trust boundary for untrusted code | `src/core/sandboxRunner.ts:53–118` creates a same-origin Blob Worker and relies on lexical restrictions around dynamic code. Worker scope has browser capabilities independent of the main window. This is a defensive source conclusion. | Default to trusted personal snippets until isolated execution is verified. Separate runner origin or process, deny ambient storage and egress by construction, enforce CPU/memory/output budgets and preserve the Apps' offline editor. [Worker scope](https://developer.mozilla.org/en-US/docs/Web/API/WorkerGlobalScope) |
| P1 · Outbound fetch policy | `server/recipeProxy.ts:189–209`, `server/icsProxy.ts:1–14` and ntfy handling in `server/index.ts:265–279` accept broad HTTP(S) destinations. No complete destination/redirect or private-network policy was found. | Route outbound fetch through one bounded, authenticated and policy-controlled service. Enforce approved destinations, redirect revalidation, response caps and safe errors. [OWASP prevention guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) |
| P1 · Blob integrity, type and caching | `server/blobs.ts:23–43` validates hash shape and writes bytes and metadata independently. `server/index.ts:208–215` returns caller-derived MIME and public immutable caching. | Verify digests from bytes, reject invalid MIME, stage atomic publication, apply protected download headers and cache controls, and enforce limits. |
| P1 · Profiles are presentation filters | `src/core/AppContext.tsx:354–372` derives visible records from a browser store that already holds the full dataset. File Hub scope and navigation groups are user-facing filters. | Classify personal/professional data and enforce sharing rights server-side and at local import/export boundaries. Treat profile filtering as convenience. |
| P1 · Sensitive relay content and configuration | `server/alarmScheduler.ts:83–101, 236–259` sends notification text through a configurable relay. Medication reminders can contain identifying schedule details. `server/index.ts:252–279` exposes configuration handlers. | Prefer local delivery and generic lock-screen text. Make relay content opt-in, keep topic secrets out of URLs shown in diagnostics, and protect configuration writes and reads. |
| P2 · Deployment permissions and cleartext | `Dockerfile:30,37` makes data locations world-writable in the image and then uses `USER node`. Android permits cleartext by configuration and workflow. | Provision writable deployment ACLs for the actual UID/GID with least privilege, and restrict cleartext to explicit local configurations. |
| P2 · Backup, photo and external-service privacy | `src/core/backup.ts` exports local settings and data. `src/core/db.ts:507–525` preserves original uploaded bytes. External recipe, barcode, exchange and weather integrations send service-specific data. | Add export disclosure/encryption options, metadata policy for shared copies, per-service consent and visibility, local retention controls and private restore verification. EXIF stripping and permission-denial behavior were untested. |

Positive controls in source include prepared SQLite statements, a hash-shaped storage path guard, DOMPurify for selected rendered HTML/SVG, and Electron context isolation. They are relevant to the paths using them. Structured route schemas, endpoint quotas, a complete data inventory and systematic isolation tests remain work.

The README’s preference for an account-free workflow is compatible with local offline operation. A remotely reachable sync service needs a separate, owner-approved pairing or identity policy that preserves that offline behavior while protecting shared or professional data.

The locked and installed versions of Fastify, DOMPurify, Vite, Vitest, React, Dexie, fflate, TypeScript and jsdom were compared for the tested snapshot. No full dependency vulnerability attestation is issued. The native wrappers resolve dependencies during packaging, and Electron has a separate manifest without a tracked lockfile. The next release gate should produce reproducible lock-based artifacts, an SBOM for web/container/native targets and an advisory review tied to exact versions. See [architecture](08_ARCHITECTURE_AND_CODE_QUALITY.md) and [issue register](03_COMPLETE_ISSUE_REGISTER.md).
