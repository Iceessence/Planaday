## PF-01 Reliable atomic saves

**Foundation · Essential foundation**

| Assessment | Proposal |
|---|---|
| Problem and intended users | One note edit can erase another even when both complete. Intended for everyone. |
| Benefit and example workflow | Edit a title and body before the first save finishes, then reopen and verify both. Repository can share its write contract with every editor. A lost-write regression has broad exposure. |
| Reuse, improvements and integration | Repository, Notes buffer, revisions, outbox. Use their existing canonical IDs, configuration and entry points where compatible. |
| Interface, architecture and database | Bind drafts to record IDs and show retry state. Preserve payload compatibility and transact record/revision/outbox. |
| Mobile and desktop | Phones keep the draft through focus and background changes. Desktop supports quick multi-panel edits. |
| Sync, performance, security and privacy | Per-record ordering and retry idempotency. Await short bounded transactions. Preserve isolation by workspace. |
| Dependencies and risk | Moderate estimated build complexity. Depends on agreed acceptance, migration and scope of foundational fixes. A lost-write regression has broad exposure. |
| Relevant product benchmarks | Notion revision history; Joplin data portability. Vendor sources and scope in the competitor review. |
| Requirement provenance | Owner brief §6, §27. Owner brief, repository baseline or proposed expansion. Approval in the standalone master specification is unknown. |
| Acceptance test | All 1,000 disjoint-write trials retain fields and monotonically advance revisions. |
